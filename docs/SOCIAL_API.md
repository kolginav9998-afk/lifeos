# Несколько аккаунтов, чат и встречи (контракт R4.2)

Документ для команд сервера и приложения. Правила проверяются тестами; протокол **нельзя ломать для старых клиентов** (старый клиент с одним аккаунтом продолжает работать).

## 1. Что хочет владелец
- Выйти из аккаунта и войти в другой (на этом же телефоне).
- Чтобы кто-то ещё мог зарегистрироваться на том же сервере, и с ним был **чат**.
- В чате **создать встречу**: цель (свидание, деловая, друзья, семья, другое), варианты мест (выбирает автор), окно дат и время; получатель открывает карточку, **выбирает дату, время и место** из предложенного, при желании пишет комментарий; автор подтверждает. Всё красиво и понятно.

## 2. Принципы
- **Сквозное шифрование**: сервер не видит ни текстов сообщений, ни содержимого встреч. Он видит: кто, кому, когда, размер.
- **Изоляция аккаунтов (требование владельца)**: у каждого человека свой аккаунт, и никто не может «просто так» смотреть что-либо о чужих аккаунтах. Нет общего каталога пользователей. Человек видит только своих **контактов**: того, кто его пригласил, и тех, кого пригласил он сам. Число аккаунтов и их имена наружу не отдаются (даже в `/v1/status`). Чужие данные, ключи, приглашения, сообщения недоступны ни по какому маршруту; на любую попытку отвечаем одинаково («не найдено»), без разницы, существует ли чужой ресурс.
- **Администратор** — первый аккаунт (создан по коду установки), то есть владелец сервера. Он видит только служебные сведения о людях на своём сервере (имя входа, дата регистрации, последняя активность, занятое место, кто пригласил) и может отключить или удалить аккаунт. Содержимое (записи, сообщения, встречи) ему недоступно: оно зашифровано ключами самих людей. Это сказано человеку при регистрации по приглашению простыми словами.
- **Приглашения, а не открытая регистрация**: на сервере с первым аккаунтом (код установки) новые аккаунты создаются только по одноразовому приглашению от существующего пользователя. Лимит аккаунтов задаёт переменная `MAX_ACCOUNTS` (по умолчанию 5).
- Данные аккаунта (журнал записей) по-прежнему зашифрованы ключом пользователя; один пользователь не видит данных другого.
- Смена аккаунта на устройстве: перед выходом приложение синхронизирует данные; если остались несохранённые, предлагает архив. Вход в **другой** аккаунт на устройстве с чужими данными: понятный выбор «стереть данные этого устройства и войти» или «отмена». Данные стёртого аккаунта остаются на сервере (зашифрованные) и вернутся при входе в него.

## 3. Сервер (`server/core.js`, `server/sqlstore.js`, `server/cloudflare/worker.js`, `server/node/server.js`)
Один Durable Object (или один файл SQLite в Node) хранит все аккаунты; таблицы получают столбец `uid`. Существующие маршруты работают как раньше для единственного аккаунта.
- `GET /v1/status` → добавить `inviteRequired` (true, когда аккаунт уже есть) и `setupCodeRequired` (true, пока аккаунтов нет). **Число и имена аккаунтов не отдаются никому.**
- `POST /v1/register`: первый аккаунт — с `setupCode` как сейчас; следующие — с полем `invite`. Имя пользователя уникально без учёта регистра. Ответ прежний.
- `POST /v1/invites` (вход) → `{ code, expiresAt }`: одноразовый код вида `XXXX-XXXX-XXXX`, срок 7 суток, не больше 5 действующих. `GET /v1/invites` — мои приглашения и их состояние (создано, использовано кем, истекло). `DELETE /v1/invites/<id>` — отозвать. Хранится только хэш кода.
- `GET /v1/contacts` (вход) → `[{ username, display, pub, since, via: 'inviter'|'invited' }]`: **только мои контакты**. Связь «контакт» возникает сама, когда человек регистрируется по приглашению (пригласивший и приглашённый становятся контактами друг друга). Других способов узнать о чужом аккаунте нет. `display` — необязательное имя для чата, которое человек выбрал сам; `pub` — публичный ключ ECDH P-256 (base64 сырой точки) или `null`, пока человек не вошёл с новой версией. `DELETE /v1/contacts/<username>` — убрать контакт (скрывает переписку и закрывает возможность писать; у второго человека связь тоже пропадает).
- Админ (только первый аккаунт): `GET /v1/admin/accounts` → `[{ username, createdAt, lastSeenAt, usedBytes, invitedBy, disabled }]`; `POST /v1/admin/accounts/<username>/disable` и `/enable`; `DELETE /v1/admin/accounts/<username>`. Для остальных эти маршруты отвечают как несуществующие (404), без намёка, что они есть. Каждое действие админа записывается в служебный журнал сервера.
- `/v1/users` **не существует** (был в раннем наброске: общий каталог отменён из-за требования изоляции).
- `POST /v1/keys` (вход): `{ pub, display? }` — опубликовать или заменить свой публичный ключ и имя.
- Чат: `POST /v1/chat/send` `{ to, ct, iv }` (ct, iv — base64; `ct` до 16 КБ) → `{ seq, ts }`. `GET /v1/chat/inbox?after=<seq>&limit=100` → `{ messages: [{ seq, from, to, ts, iv, ct }], last }` — все сообщения, где я отправитель или получатель, по возрастанию `seq`. `POST /v1/chat/hide` `{ with }` — скрыть переписку у меня (метка видимости на стороне сервера; у собеседника остаётся). Ограничения: получатель — мой контакт (иначе то же «не найдено», что и для несуществующего имени), не больше 60 сообщений в минуту с аккаунта, срок хранения 180 суток, место входит в квоту отправителя.
- `DELETE /v1/account` удаляет аккаунт, его приглашения, ключ и сообщения, где он отправитель; собеседники теряют эти сообщения (в справке это сказано).
- Безопасность: те же защитные меры, что и сейчас (блокировка подбора, одинаковые ответы для несуществующих аккаунтов, лимиты тела, HSTS). Ошибки не раскрывают, существует ли чужое имя (кроме `account_exists` при регистрации с верным приглашением). Сравнения секретов с постоянным временем; одинаковые ответы и по форме, и по размеру для «нет такого» и «это не твоё».
- Миграция: существующий единственный аккаунт получает `uid = 1`; Cloudflare и Node используют общий код (`core.js`), схема создаётся и обновляется в `sqlstore.js` без потери данных (тест миграции на копии старой базы).

## 4. Приложение: ключи и шифрование чата (`chat-crypto.js`, чистые функции + WebCrypto)
- У каждого пользователя одна пара ECDH P-256. Закрытый ключ хранится в журнале записей как запись `chatkey` (шифруется вместе со всеми данными и синхронизируется между устройствами пользователя); публичный публикуется через `POST /v1/keys`.
- Общий секрет с собеседником: ECDH (мой закрытый, его публичный) → HKDF-SHA-256 (соль = пара имён в алфавитном порядке, info = `lifeos-chat-v1`) → AES-GCM 256. Для каждого сообщения новый случайный `iv` (12 байт). Если у собеседника сменился ключ, показать предупреждение «код безопасности изменился» и не отправлять без подтверждения.
- Код безопасности: короткий отпечаток двух открытых ключей (6 групп по 4 цифры), одинаковый у обоих; его можно сверить вживую.
- Открытый текст сообщения (до шифрования) — JSON: `{ v: 1, id, kind, ts, ... }`, где `kind`:
  - `text` → `{ text }` (до 4000 знаков);
  - `meet` → предложение встречи (раздел 5);
  - `meet-reply` → `{ meetId, status: 'accepted'|'declined'|'counter', date?, time?, placeId?, other?, comment? }`;
  - `meet-status` → `{ meetId, status: 'confirmed'|'cancelled', note? }` (решает автор);
  - `read` → `{ upto: seq }` (отметка «прочитано», по желанию).
- Локальный кэш расшифрованных сообщений: отдельное хранилище IndexedDB `chat` (не журнал записей), история всегда восстанавливается с сервера по `inbox`. Опрос: при открытом приложении раз в 15 с на экране чата и раз в 60 с на фоне; бейдж непрочитанного на плитке «Чат» и на вкладке «Меню». Уведомления на телефоне, пока приложение закрыто, **не** обещаем (нет push-сервиса); это честно сказано в справке.
- Запись о встрече в журнале пользователя: `meeting` (id `mt:<meetId>`, замещаемая): `{ meetId, with, role: 'host'|'guest', type, title, status: 'proposed'|'answered'|'confirmed'|'declined'|'cancelled', when: { date, time }, place, note }`; privacy `people`, analytics false. Подтверждённая встреча появляется в «Сегодня»/календаре как событие и в `.ics`-экспорте.

## 5. Встречи (`meet.js` — чистая логика; `view-chat*.js` — экран)
Предложение `meet`:
```
{ id, type: 'date'|'business'|'friends'|'family'|'other', title, note?,
  window: { from: 'YYYY-MM-DD', to: 'YYYY-MM-DD' },          // из каких дат выбирать (не больше 60 суток)
  times: ['18:00','19:30', …] | { from:'17:00', to:'22:00', step: 30 },
  places: [{ id, name, hint?, icon? }],                      // 1–8 вариантов, которые выбрал автор
  allowOther: boolean, duration?: minutes }
```
Рабочий процесс: автор в чате нажимает «Предложить встречу» → мастер из 4 шагов (цель, куда пойти, когда, текст) с красивым предпросмотром → отправка. Получатель видит карточку (цель, автор, варианты) и выбирает дату (календарь только внутри окна), время и место (крупные плитки), может написать комментарий или отказаться или предложить своё (если `allowOther`). Автор видит ответ и подтверждает или отменяет; после подтверждения у обоих запись `meeting` со статусом `confirmed`, кнопки «Добавить в календарь (.ics)», «Напомнить за час». Все состояния имеют текст и значок, не только цвет. Типы встреч дают настроение карточки (оформление), но не меняют логику.
Чистая логика: проверка предложения (границы, повторы, пустые поля), список допустимых дат и времён, проверка ответа против предложения, переходы состояний, текстовые подписи; детерминированные тесты.

## 6. Экраны и пункты меню
- Плитка «Чат» в разделе «Люди» меню и бейдж; экран `chat`: список контактов и переписка; «Пригласить человека» (создаёт приглашение, показывает код и ссылку `…/lifeos/?invite=КОД`, кнопка «Поделиться»); «Мои встречи» (список по статусам); «Безопасность чата» (код безопасности, как это устроено). Для администратора в «Аккаунте» раздел «Люди на сервере» (имя входа, даты, занятое место, кнопки «отключить» и «удалить»; содержимого там нет и быть не может).
- Экран входа (`gate`): ссылка с `?invite=` открывает форму регистрации по приглашению; на экране входа и в «Профиле»: «Выйти и войти в другой аккаунт».
- Справка: статьи «Как пригласить человека», «Как устроен чат и что видит сервер», «Как создать встречу», «Выход и вход в другой аккаунт».

## 7. Тесты
- Изоляция (обязательно, отдельный файл `tests/server-isolation.test.mjs`): для каждого маршрута аккаунт A не получает ничего о B (синхронизация, приглашения, ключи, сообщения, контакты, число аккаунтов); не контакт не может написать; ответы для существующего и несуществующего чужого имени совпадают по коду, телу и размеру; маршруты админа для обычного аккаунта отвечают 404; `/v1/status` не содержит чисел и имён; после удаления аккаунта его данные недоступны никому.
- Сервер: `tests/server.test.mjs` расширить: регистрация по приглашению, лимит аккаунтов, одноразовость и срок приглашения, изоляция данных между аккаунтами (синхронизация A не видит B), контакты и их ограничения, публикация ключа, отправка и получение сообщений, лимиты, скрытие переписки, удаление аккаунта, миграция старой базы, одинаковые ответы для чужих имён, нагрузка на размеры.
- Приложение: юнит-тесты `chat-crypto` (шифрование туда и обратно, чужой ключ не расшифровывает, смена ключа замечается, код безопасности совпадает у обоих), `meet.js`; e2e с настоящим локальным сервером и **двумя браузерными контекстами** (A приглашает B, B регистрируется, переписка, встреча от создания до подтверждения, выход A и вход B на одном устройстве).
- Доступность и вёрстка: экраны входят в обход e2e-a11y и e2e-layout.

## 8. Честные границы
Без push-сервиса сообщения приходят, когда приложение открыто. Сервер видит, кто с кем переписывается и когда. Безопасность чата держится на ключах устройств пользователей; потеря всех устройств и пароля означает потерю закрытого ключа (после восстановления входа создаётся новый ключ, старые сообщения остаются зашифрованными старым ключом и не читаются).

## 9. Протокол сервера, как он реализован (R4.3, файлы `server/core.js`, `server/social.js`, `server/sqlstore.js`)
Если этот раздел расходится с описанием выше, верен этот раздел. Все маршруты, кроме регистрации, входа и восстановления, требуют `Authorization: Bearer <токен сессии>`.

| Маршрут | Тело или запрос | Ответ |
|---|---|---|
| `GET /v1/status` | нет | `{ app, v, registered, setupCodeRequired, inviteRequired, time }`: только «есть ли аккаунты», без числа и имён |
| `POST /v1/register` | как раньше + `invite` (для второго и следующих; для первого `setupCode`) | `201 { ok, token, expiresAt }`; без приглашения при занятом сервере `409 account_exists` (так отвечали и раньше), неверное приглашение `403 bad_invite`, лимит `403 accounts_limit`, имя занято `409 account_exists`; перебор приглашений ограничен как перебор пароля (`429 locked`) |
| `POST /v1/invites` | нет | `201 { ok, id, code, expiresAt }`; код `XXXX-XXXX-XXXX` виден один раз, на сервере его хэш; срок 7 суток; не больше 5 действующих (`429 too_many_invites`); по умолчанию приглашает только администратор, остальным `404`, пока на сервере не включено `INVITES_BY_USERS=1` |
| `GET /v1/invites` | нет | `{ invites: [{ id, createdAt, expiresAt, state: active|used|expired|revoked, usedBy }] }` |
| `DELETE /v1/invites/<id>` | нет | `{ ok }`; чужое или неизвестное `404` |
| `GET /v1/contacts` | нет | `{ contacts: [{ username, display, pub, since, via: invited|inviter|contact }] }`: только свои контакты |
| `DELETE /v1/contacts/<имя>` | нет | `{ ok }` всегда одинаково; связь убирается с обеих сторон, у удаляющего пропадает переписка |
| `POST /v1/keys` | `{ pub?, display? }` | `{ ok }`; `pub`: base64 несжатой точки P-256 (65 байт, первый байт 4), иначе `400 bad_key`; `display` до 40 знаков, пусто убирает имя |
| `POST /v1/chat/send` | `{ to, iv, ct }` (iv 12 байт, ct 16 байт…16 КБ, base64) | `201 { ok, seq, ts }`; адресат должен быть контактом, иначе `404 not_found` (так же для выдуманного имени и для себя); `429 rate` после 60 сообщений в минуту; `507 quota` |
| `GET /v1/chat/inbox?after=<seq>&limit=100` | | `{ messages: [{ seq, from, to, ts, iv, ct }], last, more }`; **номера `seq` свои у каждого аккаунта** (общего счётчика нет, по пропускам нельзя судить о чужой активности) |
| `POST /v1/chat/hide` | `{ with }` | `{ ok }`; скрывает переписку только у вызвавшего |
| `GET /v1/admin/accounts` | только администратор (остальным `404`) | `{ max, usersMayInvite, accounts: [{ username, display, role, disabled, createdAt, lastSeenAt, usedBytes, invitedBy }] }`; ни ключей, ни записей, ни сообщений |
| `POST /v1/admin/accounts/<имя>/disable` и `/enable` | | `{ ok }`; отключение закрывает сессии; себя нельзя (`400 cannot_self`); действие пишется в служебный журнал |
| `DELETE /v1/admin/accounts/<имя>` | | `{ ok }`; удаляет аккаунт, его записи, приглашения, контакты и переписку у всех |
| `DELETE /v1/account` | `{ authKey }` | удаляет свой аккаунт; администратор, пока есть другие аккаунты, получает `409 admin_has_users` |

Переменные сервера: `SETUP_CODE` (первый аккаунт), `MAX_ACCOUNTS` (по умолчанию 5), `INVITES_BY_USERS` (`1` — приглашать могут все, по умолчанию только администратор).

Хранение: таблицы `accts`, `recs (uid, id)`, `sessions (uid)`, `invites`, `contacts`, `box (uid, seq)`, `resets`, `rate`, `adminlog`. У каждого аккаунта свои счётчики журнала и почты. При первом запуске новой версии прежний единственный аккаунт и его записи копируются в новые таблицы (он становится администратором, `uid = 1`, сессии продолжают работать); прежние таблицы `account` и `records` остаются нетронутыми, чтобы можно было откатиться на прежний код. Проверяют это `tests/server-social.test.mjs` (изоляция, приглашения, переписка, администратор, перенос старой базы) и `tests/cf-local.mjs` (то же в настоящем окружении Cloudflare).
