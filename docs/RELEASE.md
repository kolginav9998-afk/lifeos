# Выпуск версии и откат

Короткий порядок для тех, кто меняет приложение (человек или ИИ-помощник). Для проверки на телефоне есть отдельный список: [CHECKLIST.md](CHECKLIST.md).

## Перед выпуском
1. `npm test` — все модульные проверки зелёные (включая сверку реестра типов с `docs/EVENTS.md`, бюджет размера, защиту от «null» в интерфейсе).
2. `npm run test:e2e` — все сценарии в настоящем браузере зелёные.
3. Поднять номер в `version.js` (`R3.x`).
4. Обновить документы: `docs/GUIDE.md` («Новое в R3.x»), `docs/CHECKLIST.md` (шаги для телефона), `docs/IDEAS.md` (строка версии), `docs/COUNCIL.md` (метки ✅/🔜/📌, итог совета).
5. Если менялся `registry.js` (добавлен тип записи), перегенерировать описание:
   ```bash
   node -e "import('./registry.js').then(m=>require('fs').writeFileSync('docs/EVENTS.md', m.registryMarkdown()+'\n'))"
   ```
6. Правило данных: новые типы записей только **добавляются**. Старые записи должны читаться всегда: это проверяет `tests/compat.test.mjs`. Если формат всё же ломается, поднять `SCHEMA_VERSION` в `events.js` и написать преобразование старых записей.

## Выпуск
```bash
git add -A && git commit -m "R3.x: что нового" && git push origin main
```
Запускаются две сборки (GitHub → Actions):
- **pages**: модульные проверки → сценарии в браузере → публикация сайта. Если проверки красные, сайт **не** обновляется.
- **apk**: проверки → сборка APK с постоянным ключом подписи → публикация «последнего APK» (ссылка постоянная).

Проверить результат без входа в GitHub можно публичным API (подставь полный хэш коммита):
```bash
curl -s "https://api.github.com/repos/kolginav9998-afk/lifeos/actions/runs?head_sha=ПОЛНЫЙ_ХЭШ" | python3 -c 'import sys,json;[print(r["name"],r["status"],r["conclusion"]) for r in json.load(sys.stdin)["workflow_runs"]]'
```

## Как работает «Обновить» в приложении
- Сборка **apk** кладёт в описание выпуска `latest-apk` первую строку-комментарий `<!-- lifeos-update {"version":"R3.x","notes":[…]} -->` (версия и список «что нового» берутся из `version.js` и `changelog.js`). Приложение читает её через GitHub API (`updater.js`), сравнивает с собой и, если версия выше, показывает «Обновить».
- Файл `lifeos.apk` скачивает нативный плагин `ApkInstaller` (`assets/android-java/ApkInstallerPlugin.java`, подключается скриптом `scripts/patch-android.py`): только с github.com / githubusercontent.com и только по https; потом открывается системный установщик Android. Подтверждение остаётся за человеком, а поставиться поверх можно только файлу с тем же ключом подписи.
- Номер сборки (`versionCode`) растёт сам (номер запуска сборки в GitHub), имя версии берётся из `version.js`. Не меняй формат первой строки описания выпуска и имя файла `lifeos.apk`: старые установленные приложения по ним ищут обновление.
- Новое в нативной части (плагины, разрешения, название и значок под иконкой) доходит до телефона тоже через «Обновить», потому что это тот же APK.

## После выпуска
- Открыть сайт: внизу экрана или в «Профиль → Версия и обновления» должна быть новая версия (если видна старая, закрыть вкладку и открыть снова: сайт обновляется при следующем запуске).
- В приложении: «Профиль → Версия и обновления → Проверить обновления → Обновить» (если в установленной версии уже есть эта кнопка). Иначе поставить APK поверх старого по ссылке (подпись та же, данные сохраняются).
- Пройти новые пункты из [CHECKLIST.md](CHECKLIST.md) и сообщить «прошло» или «не прошло» с номером пункта.

## Откат
Данные живут на устройстве и в зашифрованных копиях, а не в сборке: откат кода их не трогает.

1. Найти плохой коммит: `git log --oneline`.
2. Отменить его новым коммитом (история не переписывается):
   ```bash
   git revert ХЭШ && git push origin main
   ```
3. Сайт и APK пересоберутся автоматически (те же проверки). Телефон получит прежнюю версию при следующем запуске сайта и после установки свежего APK поверх.
4. Записи, созданные новой версией, остаются в данных. Прежняя версия их не показывает, но и не удаляет: после повторного обновления они снова видны. «Проверка данных» в настройках показывает, сколько записей незнакомого типа.
5. Копию, сделанную более новой версией, прежняя версия открыть откажется (защита от тихой порчи). Сначала обнови приложение.

Перед крупным обновлением полезно сделать зашифрованную копию: «Ещё → Резервные копии → Сохранить зашифрованную копию».

## Границы бесплатного тарифа и размера
- Сайт и APK грузят одни и те же файлы; бюджет размера проверяется тестом (`tests/size.test.mjs`).
- Сервер синхронизации (Cloudflare, см. [SERVER.md](SERVER.md)) пока не развёрнут: до этого данные живут только на устройстве.

## Если меняется формат данных
Новые типы записей и новые поля **не требуют** миграции: старые записи читаются как есть (так устроен журнал событий). Миграция нужна, только если старые записи нельзя читать без преобразования (переименовано или переосмыслено поле).

1. Подними `SCHEMA_VERSION` в `events.js` на единицу.
2. Добавь в `MIGRATIONS` (`migrate.js`) шаг `{ from: N, to: N+1, note, up }`: функция берёт список записей схемы N и возвращает записи схемы N+1, исходный список не меняет.
3. Добавь тест с примером старой копии. Тест `миграции: цепочка без дыр` упадёт, если забыть шаг.
4. Восстановление из копии прогоняет миграции автоматически и пишет «Формат копии обновлён».

Копию более новой версии приложение отклоняет с просьбой обновиться. Локальные данные на телефоне не версионируются отдельно: они живут как набор записей.
