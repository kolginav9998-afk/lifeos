# Решения по архитектуре (ADR)

Короткие записи: что решили, почему и чем это проверяется. Если решение меняется, добавляй новую запись, а не стирай старую.

## ADR-1. Один код для сайта и Android-приложения
- **Решение:** веб-приложение (PWA) одно; Android-APK собирается из тех же файлов через Capacitor.
- **Почему:** нужно, чтобы на телефоне и в браузере всё работало одинаково, а любое изменение проверялось один раз.
- **Следствия:** native-возможности (уведомления, файлы) подключаются через `platform.js` и работают, только если доступны; всё остальное одинаково.
- **Проверка:** `scripts/build-web.sh` собирает сайт и APK из одних файлов; `pages.yml` и `apk.yml` запускают одни и те же тесты.

## ADR-2. Журнал событий как единственный формат данных
- **Решение:** всё хранится записями `{id, type, ts, payload, source, confidence, evidence}`. Новые типы только добавляются, существующие поля не переименовываются.
- **Почему:** синхронизация, экспорт и откат проще, когда данные одинакового вида; старые записи читаются всегда («обновление не должно стирать данные»).
- **Следствия:** все типы описаны в [EVENTS.md](EVENTS.md) (из `registry.js`); записи незнакомых типов (от более новой версии) сохраняются и не мешают; копия из более новой версии открывается только после обновления приложения.
- **Проверка:** `tests/compat.test.mjs` (старые форматы), `tests/registry.test.mjs` (реестр совпадает с кодом и документом).

## ADR-3. Без сборщика, без внешних библиотек и адресов
- **Решение:** обычные ES-модули без бандлера; в коде нет `innerHTML`, `eval`, внешних адресов и сетевых вызовов, кроме клиента сервера синхронизации и офлайн-кэша.
- **Почему:** безопасность (строгая политика CSP), прозрачность кода для проверки, работа без интернета.
- **Следствия:** интерфейс строится через `el()`; списки с «необязательными» элементами собираются через `fill()` (иначе `null` превращается в текст).
- **Проверка:** `tests/static.test.mjs` (запрещённые конструкции, внешние адреса, `null` в `replaceChildren`), `tests/size.test.mjs` (бюджет размера), `tests/deps.test.mjs` (нет циклов, соблюдены слои).

## ADR-4. Шифрование на устройстве, сервер не видит данные
- **Решение:** пароль превращается в ключ (PBKDF2-SHA256, 600 000 итераций), записи шифруются AES-256-GCM; сервер синхронизации хранит только зашифрованные записи.
- **Почему:** в данных здоровье, деньги, дневник и мысли.
- **Следствия:** забытый пароль восстановить нельзя; резервные копии шифруются отдельным паролем; потеря кода восстановления аккаунта означает потерю доступа.
- **Проверка:** `tests/crypto.test.mjs`, `tests/e2e-security.mjs` (на диске нет открытого текста), `tests/server.test.mjs`, `tests/e2e-sync.mjs`.

## ADR-5. Сайт выкладывается только после проверок в настоящем браузере
- **Решение:** `pages.yml`: модульные тесты → сценарии в Chromium → публикация. Красные проверки не пускают обновление на сайт.
- **Почему:** пользователь не программист, проверка на телефоне дорогая, а ошибки в данных недопустимы.
- **Следствия:** каждая новая функция получает тест логики и сценарий; на телефоне пользователь проверяет только то, чего автотест проверить не может (уведомления, вид, жесты).
- **Проверка:** `docs/RELEASE.md`, `docs/CHECKLIST.md`.

## ADR-6. Аналитика осторожная: связь, а не причина
- **Решение:** сравнение только с самим собой (личная норма: медиана и MAD), поправка на множественные сравнения, интервалы для оценок, формулировки «связь, не доказанная причина», дни болезни исключаются.
- **Почему:** на малых данных легко увидеть закономерность там, где её нет.
- **Следствия:** выводы появляются после нескольких недель отметок; есть личные эксперименты (фазы A/B в случайном порядке) для проверки гипотез.
- **Проверка:** `tests/stats.test.mjs`, `tests/bt-analytics.test.mjs`.

## ADR-7. Никаких диагнозов и лечебных советов
- **Решение:** приложение считает и показывает цифры, а советы даёт только общие (сон, движение, обращение к врачу) и всегда как предложение. Тесты не диагностика и не IQ.
- **Почему:** безопасность пользователя и честность.
- **Следствия:** в тексте нет слов «диагноз/лечение» как обещаний; при долго низком настроении приложение направляет к близким и специалистам.
- **Проверка:** тексты в `reflect.js`, `thoughts.js`, `prevent.js`, `emergency.js` и тесты на их содержание.

## ADR-8. Внутри приложения нет ИИ: разбор по правилам и подтверждение человеком
- **Решение:** «умный ввод» понимает фразы по правилам и предлагает действие; сохраняется только после нажатия.
- **Почему:** приватность (ничего не уходит наружу), работа без интернета, предсказуемость.
- **Следствия:** для работы с ИИ-репетитором в курсах есть готовые запросы для копирования; данные в чужие сервисы приложение не отправляет.
- **Проверка:** `tests/capture.test.mjs`, статическая проверка сетевых вызовов.

## ADR-9. Постоянный ключ подписи APK
- **Решение:** APK всегда подписывается одним и тем же ключом (отпечаток проверяет сборка), «последний APK» лежит по постоянной ссылке.
- **Почему:** Android ставит обновление поверх, только если подпись совпадает; иначе данные пришлось бы вводить заново.
- **Проверка:** шаг «Проверить, что подпись — наш постоянный ключ» в `apk.yml`.

## ADR-10. Миграции формата вместо «ломающих» изменений
- **Решение:** новые типы и поля только добавляются; если старые записи нельзя читать как есть, повышается `SCHEMA_VERSION` и пишется шаг в `migrate.js`. Копии старых версий проходят миграции при восстановлении, копии новее приложения отклоняются.
- **Почему:** данные должны переживать любые обновления; единственное место, где старый формат встречается снова, — файл резервной копии.
- **Следствия:** миграция не меняет исходный список и проверяется на примере старой копии; результат миграции снова проходит проверку записей.
- **Проверка:** `tests/r39.test.mjs` («миграции…»), `docs/RELEASE.md` («Если меняется формат данных»).

## ADR-11. Часы и память устройства: только подсказки
- **Решение:** приложение замечает записи «из будущего», откат часов назад и нехватку места, но ничего не исправляет само.
- **Почему:** время и место принадлежат системе телефона; тихая «починка» порядка записей хуже явного предупреждения. Неверные часы ломают порядок записей, напоминания и синхронизацию.
- **Проверка:** `devicetime.js`, `storageinfo.js` (чистая логика) и тесты в `tests/r39.test.mjs`. Файл `clock.js` — другое: логические часы синхронизации.

## ADR-12. Загрузка архива по умолчанию только добавляет
- **Решение:** загрузка архива добавляет новые записи и не трогает уже имеющиеся. Если ничего не затирается, загрузка проходит сразу. Записи, отличающиеся от имеющихся, заменяются только по явному выбору, после показа того, что внутри. Режим «только проверить» ничего не меняет.
- **Почему:** главный риск восстановления из старой копии: тихо вернуть старые версии поверх новых правок. Для человека без технических навыков безопасный вариант должен быть вариантом по умолчанию.
- **Следствия:** настройки в архиве применяются сами только на пустом устройстве; в архив входят лишь настройки внешнего вида и времени напоминаний, без привязанных к устройству.
- **Проверка:** `tests/archive.test.mjs`, `tests/e2e-archive.mjs`, `tests/fuzz.test.mjs`.

## ADR-13. Навык подтверждается карточками, а не отметкой «пройден»
- **Решение:** навык из урока предлагается, когда урок пройден и выучено не меньше 80% его карточек (коробка 4 и выше: повторение раз в две недели и реже). Всё остальное человек добавляет сам.
- **Почему:** «точно изучил» нельзя определить по одной отметке. Интервальные повторения дают проверяемый признак.
- **Проверка:** `tests/skills.test.mjs`.

## ADR-14. Второе окно: подтягиваем записи, а не блокируем
- **Решение:** окна одного приложения считают друг друга (`BroadcastChannel`) и после записи в одном окне другие перечитывают данные. Окно не блокируется: просто видна подсказка.
- **Почему:** блокировка вторым окном раздражает и ломается при зависшем окне; общая картина данных безопаснее. Запись идёт по одной записи, поэтому окна не затирают друг друга целиком.
- **Проверка:** `tests/safety.test.mjs`, `tests/e2e-r311.mjs`.

## ADR-15. Вход обязателен, но проверяется на устройстве
- **Решение:** приложение открывается только после входа в аккаунт (флаг сборки `REQUIRE_ACCOUNT`, выключается только для автотестов). Уже привязанное устройство открывается без сети: входом считается привязка аккаунта на устройстве (и пароль защиты, если он включён). Выход закрывает приложение, но не стирает данные.
- **Почему:** так просил владелец; один аккаунт на сервере и шифрование на устройстве делают вход смысловым. Требовать сеть при каждом запуске было бы вредно: приложение должно работать офлайн.
- **Следствия:** это правило интерфейса, а не защита данных на диске: от чужих рук защищает пароль защиты (шифрование). Данные устройства при входе не теряются: подходящие остаются, неподходящие сначала сохраняются зашифрованной копией. Экран входа использует те же формы, что и профиль, с другими `id` (`gate-…`).
- **Проверка:** `tests/e2e-gate.mjs` (настоящий сервер: регистрация, перезапуск, выход, вход, второе устройство, сервер недоступен).

## ADR-16. Обновление изнутри: GitHub Releases и системный установщик
- **Решение:** сборка публикует APK в выпуск `latest-apk` и кладёт в описание строку `<!-- lifeos-update {...} -->` с версией и списком изменений. Приложение читает её через GitHub API, скачивает файл (только с GitHub, по https, с проверкой размера и контрольной суммы) и открывает системный установщик Android через нативный плагин `ApkInstaller`.
- **Почему не тихое обновление веб-части подменой файлов:** такое обновление не меняет нативную часть (разрешения, название, значок, плагины) и требует сложного отката при поломке; обычная установка поверх проверяется самим Android (тот же ключ подписи, данные сохраняются) и покрывает всё. Цена — подтверждение установки: убрать его нельзя, так устроен Android.
- **Следствия:** формат первой строки описания выпуска и имя файла `lifeos.apk` нельзя менять: по ним старые установленные приложения ищут обновление. `versionCode` растёт с номером запуска сборки.
- **Проверка:** `tests/r312.test.mjs`, `tests/e2e-update.mjs` (Android-часть подменена), сборка APK в CI компилирует плагин.

## ADR-17. Оформление: токены, проверяемый контраст, название в одном месте
- **Решение:** цвета, радиусы и тени заданы токенами в начале `style.css` (светлая и тёмная темы), компоненты используют только токены. Контраст ключевых пар цветов проверяется тестом (WCAG AA, 4,5:1). Название приложения лежит в `config/brand.json`: сборка подставляет его в страницу, манифест и подпись под иконкой.
- **Почему:** красивый вид не должен ломать читаемость; переименование не должно требовать поиска по десятку файлов. Технические имена (`app.lifeos.mobile`, адрес сайта, имя файла APK) не меняются: иначе обновление поверх старого приложения и данные сломаются.
- **Проверка:** `tests/r313.test.mjs`; вид экранов смотрится скриншотами (`tests/shots.mjs`, `tests/shots-gate.mjs`).


## ADR-18. Бюджет размера 2,3 МБ, несколько таблиц стилей, курсы «с нуля» как данные
- **Решение:** общий бюджет веб-кода поднят с 1,4 до 2,3 МБ (предел на один файл остаётся 64 КБ). Стили разбиты на `style.css` (основа и токены) и дополнения `style-design.css`, `style-a11y.css`, `style-help.css`, `style-zero.css`, `style-diction.css`, подключённые в `index.html` в этом порядке. Курсы «с нуля» лежат файлами данных `c-zero-*.js` и частями `zero-xx-*.js`, их правила проверяет `zero-kit.js`.
- **Почему:** учебное содержимое (английский с нуля около 150 КБ, иврит около 200 КБ) — это сам смысл приложения; сжимать его нельзя, а один 64-килобайтный файл стилей уже был заполнен на 90 %. Сервис-воркер кэширует всё один раз, на повторных запусках сеть не нужна.
- **Цена:** стартовая загрузка и разбор растут (около +40 %). Замер на слабом телефоне не снят: если запуск станет медленным, следующий шаг — загрузка курсов по требованию (динамический `import`), а не урезание содержимого.
- **Проверка:** `tests/size.test.mjs` (общий и поштучный пределы), `tests/static.test.mjs` (каждая таблица стилей подключена), `tests/deps.test.mjs` (файлы курсов зависят только от `zero-kit.js` и своих частей), `tests/zero-kit.test.mjs`.
- **Дополнение R4.1:** бюджет поднят до 3,2 МБ: добавлены «Дом», «График» и «Зарплата», тесты на логику, профиль со статистикой, чат и встречи. Когда веб-код подойдёт к 3 МБ, следующий шаг не новое повышение, а ленивая загрузка редких экранов (динамический `import()` при первом открытии), чтобы запуск оставался быстрым.

## ADR-19. Быстрый вход по отпечатку: плагин NativeBiometric, отпечаток как отдельная проверка перед чтением пароля
- **Решение:** в Android-приложении можно включить вход по отпечатку вместо пароля (на экране блокировки, при входе в аккаунт и в «Профиле» → «Быстрый вход»). Используется плагин `@capgo/capacitor-native-biometric` версии 7.6.0 (последняя для Capacitor 7; версия закреплена точно, потому что это нативный код: обновлять только осознанно). Окно отпечатка показывает сама система (BiometricPrompt, только «сильная» биометрия, без запасного входа по коду телефона). Пароль и логин аккаунта лежат в хранилище плагина, отметка «включено» — в настройках устройства (`quickUnlock`: не едет в архиве и не синхронизируется). Пароль всегда остаётся запасным путём, а ошибки отпечатка (отмена, «слишком много попыток») никогда не считаются неверными попытками пароля: `vault.js` не менялся.
- **Что показала разведка (код плагина 7.6.0 прочитан целиком, чужой код не запускался):**
  - **Совместимость со сборкой:** `peerDependencies` `@capacitor/core >=7.0.0`; Gradle плагина: AGP 8.7.2, compileSdk 35, minSdk 23, targetSdk 35 (значения берутся из корневого проекта, если они там заданы) — ровно то, что ставит шаблон Capacitor 7.6 (AGP 8.7.2, Gradle 8.11.1, minSdk 23, compileSdk 35). Упакован так же, как официальные плагины (`android/build.gradle` и `android/src/main`), так что `scripts/patch-android.py` не должен менять `minSdk` и другие числа. Тянет за собой androidx.biometric 1.1.0, material 1.9.0, constraintlayout и navigation: APK станет заметно больше (точный размер покажет сборка).
  - **Лицензия — не MIT и не Apache, а MPL-2.0** (слабый копилефт на уровне файлов): пакет берём как есть и не правим, на остальной код приложения лицензия не распространяется; обязательство остаётся одно: если когда-нибудь править файлы самого плагина, правки нужно публиковать. Запасной `capacitor-native-biometric` (MIT) сделан для Capacitor 3 (последняя версия 4.2.2, 2023 год): в его Gradle прописаны AGP 3.6.1 и `jcenter()`, compileSdk 29; с нашей сборкой несовместим, не подходит.
  - **Манифест:** плагин добавляет только окно `ee.forgr.biometric.AuthActivity`; разрешение `USE_BIOMETRIC` сам НЕ объявляет (README требует вписать его в манифест приложения): это делает `scripts/patch-android.py`. `USE_FINGERPRINT` плагин не объявляет, но его может принести библиотека androidx.biometric: `scripts/check-apk.mjs` допускает его как необязательное. Какие именно разрешения и открытые окна принесёт androidx.biometric, без Android SDK проверить нельзя (Google Maven из этой среды недоступен): окна `AuthActivity` и `androidx.biometric.DeviceCredentialHandlerActivity` в манифесте приложения явно закрываются (`exported=false`, `tools:replace`), а проверку итогового APK сделает CI.
  - **Где и как хранится пароль:** `setCredentials` шифрует каждое значение AES-256-GCM; ключ создаётся в Android Keystore под именем записи (у нас `app.lifeos.mobile`), в защищённом модуле телефона, где он есть (StrongBox), и не покидает хранилища; на Android 9–11 и 15+ ключ дополнительно пригоден, только пока телефон разблокирован (на 12–14 плагин сам это отключает из-за известных сбоев). Зашифрованные строки лежат в закрытой памяти приложения (`SharedPreferences` «NativeBiometricSharedPreferences»). Облачное копирование и перенос на другой телефон у приложения выключены, поэтому они никуда не уезжают. `deleteCredentials` удаляет ключ и стирает ВСЕ значения плагина.
  - **Привязан ли доступ к отпечатку на уровне ключа: НЕТ.** Ключ создаётся без `setUserAuthenticationRequired`, а `getCredentials` отпечаток не спрашивает: отпечаток проверяет отдельный вызов `verifyIdentity`, и только код страницы решает читать пароль после него (в коде плагина есть вариант с ключом, привязанным к отпечатку, но он нигде не вызывается). Поэтому защита держится на коде приложения, а не на железе.
  - **Известная слабость плагина:** начальный вектор GCM у всех значений один и тот же (нули). По двум зашифрованным значениям из файла можно узнать их «разность»; чтобы она ничего не раскрывала, в поле «логин» плагина мы кладём случайную строку, а настоящие логин и пароль — одним значением в поле «пароль».
  - **Окно отпечатка:** по умолчанию плагин закрывает окно после ОДНОЙ неудачи с кодом 4 («слишком много попыток»): ставим `maxAttempts: 3`. Лицо принимается только на телефонах с надёжным («сильным») распознаванием лица; обычное лицо на большинстве телефонов не подойдёт, приложение скажет об этом словами.
- **Что это даёт:** не нужно набирать длинный пароль каждый день; пароль нигде не лежит открытым и не попадает в архив, настройки и на сервер; зашифрованные значения без ключа телефона прочесть нельзя; посторонний, взявший разблокированный телефон, не откроет закрытое приложение, если его отпечатка нет среди записанных.
- **Чего это НЕ даёт (честно):**
  - Кто знает код разблокировки телефона, может добавить в телефон свой палец и открыть приложение; открывает любой записанный в телефоне отпечаток, добавление и удаление пальцев вход не отзывает.
  - Отпечаток не связан с ключом: код, исполняющийся внутри приложения (вредная программа с правами владельца, телефон с root, внедрённый скрипт), может прочитать пароль без окна отпечатка. На телефоне с root защита слабее.
  - Пароль на телефоне хранится в восстанавливаемом виде (иначе им нельзя войти). Кому нужна наибольшая защита, этот вход лучше не включать.
  - Не проверено на настоящем телефоне: окно отпечатка, чтение и запись в Keystore, поведение на разных марках и версиях Android проверит только владелец.
- **Почему так, а не иначе:** надёжнее было бы привязать ключ к отпечатку (Keystore с `setUserAuthenticationRequired` и окно с криптообъектом), но готового плагина с этим нет, а свой нативный код нельзя собрать и проверить без Android SDK и телефона; это следующий шаг, если нужна наибольшая защита. Хранить пароль в странице (localStorage, IndexedDB) хуже: он лежал бы без аппаратной защиты.
- **Следствия:** формат хранения данных и протокол сервера не менялись. Имя записи `app.lifeos.mobile` и формат значения `{"v":1,"u":логин,"p":пароль}` менять нельзя: прежние записи перестанут читаться. Быстрый вход сам выключается (и пароль стирается из хранилища телефона) при смене пароля, восстановлении по коду, выходе из аккаунта, удалении аккаунта на сервере, отключении защиты и стирании данных; если сохранённый пароль перестал подходить (его сменили на другом устройстве), вход выключается с понятным сообщением.
